## 引き出しを増やすためのルール

1. **外部コードを読む**：READMEだけを読んだ場合は「実装未確認」と記し、推測で実装内容を補わない。公式データシートも照合する。
2. **DinMeterと比べる**：単に「同じ機能がある」ではなく、状態管理・演算場所（チップ/マイコン）・MIDI送信方式・音楽的な使い方の違いを示す。
3. **使いどころを書く**：具体的な音作り・不具合・UI設計の問題を解決するとき、何を使うとよいか書く。
4. **事実を区別する**：「ソースで確認済み」「論理的な推論」「仮説」「反証」「実機試験待ち」を混在させない。
5. **否定的な知見も保存**：「使えない理由」「採用しない理由」「他の説明が有力」も次の開発で役立つ。
6. **重複を防ぐ**：原典と詳細はレビューに、再利用可能な考え方は`knowledge/`の短いカードに置く。新しい情報がない日は無理にファイルを増やさない。
7. **コード変更は別判断**：ここは調査と設計判断の保管場所。実装の修正やプリセット変更はしない。第三者コードのライセンスにも注意する。

## 新しい知見カードの形式

- **タイトル／分類／成熟度**（既存コード確認・仮説・実機試験済み）
- **何に使える？**（演奏上の効果、具体的な困りごと）
- **仕組み**（原典の関数・パラメータ・処理順序）
- **現行DinMeterとの差**（置き換えるのか、組み合わせるのか）
- **採用条件**（メリット、欠点、制約、ライセンス）
- **反証・不確実性**（その考え方が間違っている可能性）
- **実験・導入するときの手順**（まだ試していなければ未実施と明記）
